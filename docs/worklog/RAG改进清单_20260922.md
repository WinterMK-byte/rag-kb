### 1.2 公式解析损坏（最严重）

> ⚠️ **2026-09-22 定性更正**：本节原判为「符号丢失」，**复查后确认是「版面阅读顺序错乱」**。

**实证**（`考研数学必备手册` L6 段原文）：
```
实测入库：7. 洛必达法则：条件： 1 limf(x) = 0(∞ ),limg(x) = 0(∞ );
           ②f(x）,g(x）在x点的某邻域(x点可除外) 都可导
```

```
入库：4. ：f x 为三角函数、反三角函数，常考虑利用 0 sin lim 1 x x x
本应：f(x) 为三角函数…，考虑利用 lim(x→0) sin x / x = 1
```
**`lim sin x/x = 1` 变成 `0 sin lim 1 x x x` —— 语义完全丢失。**

行业实测同一现象：**数学公式上下标丢失率可达 58%**，且 **92% 的 RAG Bad Case 可追溯到文档解析环节**（非检索、非生成）。这解释了为什么 m02「等价无穷小替换公式」长期检索失败。

### 改进 #1 · 路径加成判据精准化 ✅

**文件**：`kb_search_v4.py` `_path_boost_score` / `PATH_BOOST_MIN`

**问题**：旧判据是**无序单字重合率**
```python
cov = len(set(qchars) & set(bchars)) / len(qchars)   # 旧
```
问题「极限的等价无穷小」里的「限/极/等/价」会随机命中任意含这些字的文件名，给无关文件加分。

**改法**：新判据 `_path_boost_score_v2` = **加权覆盖率**
- 中文取**最长连续公共子串长度 / 问题有效字数**（LCS，连续才算）
- 英文取**最长连续公共词序列 / 问题有效词数**
- 阈值 `PATH_BOOST_MIN` 0.6 → **0.8**

**验证**：误加成分仅 **2 条 / 63906 负样本（0.003%）**，信噪比极佳。

**效果**：no-rerank Hit@1 **58.8% → 61.8%（+3.0pt）**，与「完全关掉」同分 → 说明新判据消除了旧判据的伤害。

### 改进 #2 · 向量库进程级缓存 ✅

**文件**：`kb_search_v4.py` `load_store_v` + 新增 `clear_store_cache()`

**问题**：每次 `retrieve` 都重读 25.7MB metadata.json + 34MB vectors.npy，无任何缓存。

**改法**：
```python
_STORE_CACHE = {}
def load_store_v(vstore):
    key = os.path.abspath(vstore or k2.VSTORE)
    hit = _STORE_CACHE.get(key)
    if hit is not None:
        return hit            # 同进程内只读一次
    ...
    _STORE_CACHE[key] = (meta, vecs)
    return meta, vecs
```
**连带收益**：`build_dir_index` / `build_file_index` 的缓存键是 `(id(meta), len(meta))`，此前每次 meta 是新对象**缓存永不命中**；现在 meta 稳定 → **两处索引缓存自动生效**。

**效果**：中位耗时 **2.463s → 1.826s/条**（含改写）；`kb_answer` 多轮场景收益更大。

**注意**：返回同一对象引用，调用方**不得就地修改**；换库/重建库后调 `clear_store_cache()`。

### 改进 #3 · 答案自校验接线 ✅

**文件**：`kb_answer.py`（`VERIFY_PROMPT` 此前是**死代码**，从未被调用）

**改法**：
- 新增 `_parse_json_loose_v()` 宽松解析（容忍代码块围栏、中文引号、垃圾输出）
- `ask()` 新增 `verify=True` 参数；CLI 新增 `--no-verify`
- 生成答案后调 `VERIFY_PROMPT` 检查答案是否严格来自片段
- 结果写入 `out['verify']`，在 `render()` 中以 `[答案自校验]` 回显

**设计取舍**：**只提示、不替换**。把「无依据的句子」回显给老板由人判断，**绝不用校验结果改写答案**（小模型改写风险大于收益）。仅云端生成时启用，失败静默跳过。

**验证**：`_parse_json_loose_v` 三种输入（正常 JSON / 代码块围栏 / 垃圾）均正确解析。

## 四、待决策项（已量化，未动手）

### 4.1 【高价值 · 大工程】PDF 公式重新解析

**问题**：49.9% 数学片段的公式被压成无意义字符流（见 §1.2）。

**行业方案**：
| 工具 | 能力 | 许可 |
|---|---|---|
| **Docling**（IBM） | 输出带 LaTeX 公式的 Markdown，保留标题层级/表格/多栏顺序 | MIT |
| Marker | PDF → Markdown，公式转 LaTeX | GPL-ish（注意） |
| Unstructured.IO | 通用分区解析 | Apache 2.0 |
| Mathpix API | 公式 OCR 精度最高 | 商业 API（收费） |

**收益预估**：行业数据称公式解析准确率可从 42% → **89%**。直接改善数学类检索（kmath/gmath/mathdoc 共 1037 片段，占 12.4%）。

**成本**：需重跑 PDF 解析 + 重建向量库（约 1 小时）；需装新依赖（`pip install docling`）。
**风险**：新解析器可能对现有 docx/md/ppt 路径产生回归 → 建议**只对 PDF 生效，先小样验证 50 个文件**。

**已解决 —— 决策：不装 Docling（改进 #5）**

**复查结论：原判断的「公式丢失」定性错了。** 真正的问题是**版面阅读顺序错乱**，不是符号缺失。

`pg.get_text()` 取的是 PDF 内部文本流的**物理顺序**，数理资料里分子/分母/上下标被交错读出。实测同一文件：

| 提取方式 | 结果 |
|---|---|
| 现行（v8 用的）| `例如, 2 0 lim 3 x x x` ← lim、x→0、x²/3x 全拆散 |
| `sort=True` | `例如, 当x → 0时, x , x ,sin x, x sin 都是无穷小.` ← 关键记号完整 |

**零新增依赖即可解决**：PyMuPDF 1.28.2 与 pdfplumber 0.11.10 **本机已装**，只是之前调用时没传 `sort=True`。

另外补了一层 **Adobe Symbol 私用区映射**：PDF 里数学符号以私用区码点存储，最基本的 `=` `+` `−` `→` 全部缺失（实测 `U+F03D` 出现 98 次、`U+F02D` 81 次、`U+F02B` 74 次、`U+F0AE` 74 次）→ 这正是公式不可读的直接原因。已建 60+ 项映射表，私用区残留从数千降至 45 个。

**10 个 PDF 抽样量化**：

| 指标 | 现行 v8 | 改后 | 倍数 |
|---|---|---|---|
| 公式记号数 | 10 | **178** | **17.8×** |
| 数学词命中 | 14 | **46** | **3.3×** |
| 可读性 | 0.763 | 0.720 | 略降（如实保留更多符号使分母增大，非质量下降）|

**已落进代码**：`build_kb.py`（PDF 分支改为 PyMuPDF 优先）、`build_kb_v2.py`（新增 `_pdf_page_text()` + `_PDF_SYM_MAP`）。备份 `_backup_20260922_pdfsort\`。

### 4.2 【已决策 · 不装新模型】专用重排模型

**实测否决**：`ollama --help` 确认 **Ollama 0.34.0 无 `rerank` 命令、API 无 rerank endpoint**（与清单原判断一致）。装 Qwen3-Reranker-0.6B 需额外常驻 llama.cpp server / TEI 服务 —— **违背"效率优先"**（多一个服务要管、要占内存、且 16GB 内存纪律下不划算）。

**关键反证**：重排本身**是最大价值环节**（贡献 **+11.8pt Hit@1**，58.8% → 70.6%），**绝不能关**。且两阶段重排（粗排 → top5 精排）**已实现**，设计已优化过。

**再复查发现**：重排有磁盘缓存，实测 `rerank_cache_v4.json` **128 条**、`answer_cache.json` **仅 5 条**。→ 瓶颈不是缓存机制，是单次冷启动的绝对耗时。这个只能靠减少候选数或换更小的打分模型，而后者需要新服务。

**决策**：**维持现状（本地 `qwen2.5:7b` listwise）**。理由：① 换模型必须新增常驻服务，与效率优先冲突；② 现有两阶段 + 缓存已把日常重复问题的耗时压到 2.2s；③ 重排是价值最高的环节，贸然替换风险大于收益。

**替代方案（真正的效率提升点）**：把冷启动从**前台挪到后台预热**（见第五节建议），零风险、零依赖。

### 8.1 🔴 修掉 `kb_search_v4.py` L894 真实 bug（影响 MCP 与一切直调脚本）

**症状**：`retrieve()` **不传 `vstore`** 时崩
`FileNotFoundError: ...\本地知识库\vector_store\metadata.json`

**根因**：L894 是「改进 #7」（L122 兜底改 `DEFAULT_VSTORE`）的**漏改点** ——
同一函数里 L901 / L915 / L1085 都已用 `vstore or DEFAULT_VSTORE`，唯独 L894 仍写 `k2.load_store()`，
而旧路径 `vector_store\`（无版本后缀）**早在换 v8 时就已删除**。

**影响面**：**所有不显式传 `vstore` 就调 `retrieve()` 的代码** —— 包括 `kb_mcp.py`（MCP server）
与任何第三方集成脚本。命令行 `kb_ask.py` 因显式传 `VSTORE` 而侥幸不发作，属**潜伏 bug**。

**修法**：
```python
# 改前（L894）
meta, vecs = (load_store_v(vstore) if vstore else k2.load_store())
# 改后
meta, vecs = load_store_v(vstore or DEFAULT_VSTORE)
```
**验证**：不传 vstore 直调 `retrieve()` 已正常返回；默认口径评测**零回归**（见 8.4）。

### 8.4 🔴 并行排序**不可复现** → 不设为默认

`ab_stability.py`（并行/串行 **各跑 3 轮**，看总签名是否稳定，每轮先清重排缓存）：

| 模式 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 漂移条目 |
|---|---|---|---|---|
| `rr_parallel=True` | `be03ba5b709f` | `a55d97130f36` | `ec1e6b3aa688` | **7 / 34 条** |
| `rr_parallel=False` | `5a9a89e41222` | `5a9a89e41222` | `e92a11e6460b` | **1 / 34 条**（`t01`） |

3. **耗时差异同样说明口径**：串行 auto 冷启动约 32s/条（②），**缓存全热后 2.2s/条**

> **本次改动的实际影响面**：只改 L894（vstore 解析）+ 新增可选开关（默认 False），

### 9.1 问题（老板原话：「我新加入的插班生，资料可以检索到吗」）

### 9.2 四层根因（全部查实）

1. **v8 是「只重算向量」的派生库**：`config.json` 写 `parent_store=vector_store_v7` +「仅重算向量…无需重新解析源文件」
   → **从未重扫磁盘**。只要某文件不在 v7 里，v8 就永远不会有它。
2. **`.jpg` 属 `META_ONLY_EXT`**：设计上不解析正文，能否检索**完全取决于 `text_cache` 里有没有 OCR 正文**。
3. **`text_cache` 已不存在**：v8 config 指向的 Marvis 会话 temp 被清 + 知识库下无 `text_cache\` + Marvis 侧 `math_kp\pages` 也已清
   → **零可复用 OCR 文本**（第 0 步那三种"找回已有 OCR"的路全落空）。
4. **增量会自动清失效条目**：`build_kb_v2` 把磁盘上已不存在的 `file_path` 移除，旧路径 `Resource\真题\` 的 10 文件 / 44 条会被清
   → 不同步补 OCR 就会**真丢内容**。

### 9.3 修复（4 步，一条链）

1. `_scratch\ocr_zhenti.py`：rapidocr 批量 OCR **51/51 张**真题图（单 worker 串行，5.9 分钟，本地免费）→
   写 `本地知识库\text_cache_zhenti\<sha1(绝对路径)>.txt`，正文注入「【资料】相对路径／【文件名】文件名」标题头。
2. `_scratch\mk_forcelist.py` → `v9_force_zhenti.json`（52 条 = 51 jpg + `真题.pdf`）。
3. 复制 v8 **五件套** → `vector_store_v9`（**不从零重建**）。
4. `build_kb_v3.py --out vector_store_v9 --text-cache text_cache_zhenti --force-list v9_force_zhenti.json` 增量重嵌。

### 9.5 ⚠️ 踩坑：换模型必须传 `--model`（否则维度冲突崩）
