## 一 · 🔴 一个必须先知道的坑：text_cache 只覆盖 233/2046 文件

```
text_cache_zhenti2\  →  233 个 .txt（1.6 MB）
vector_store_v10\    →  8618 片段 / 2046 文件
```

- `text_cache/<sha1>.txt` 是**提取缓存**（含 OCR 结果），命中即不重复解析（`build_kb_v2.py` L10/L139）。
- 现役 `text_cache_zhenti2` **只有 233 个 txt** → 大量文件是**每次实时解析**（PDF/Office 现场提取）。

**→ 所以「只清洗 text_cache 就完事」是错的。** 正文清洗必须落在**解析出口**上，有三条路径：

## 二 · 三条实现路径（按推荐度排序）

### 路径 A（推荐）：在 `build_kb_v2.py` 的正文出口加清洗钩子

**做法**：在 `build_kb_v2.py` 里，凡得到正文 `text` 的地方（缓存命中 / 现场解析两条出口）
统一过一遍 `text_clean.clean_text()`。

- **优点**：① 覆盖**全部**文件（不管走不走缓存）；② 源头干净，后续重建也干净；
            ③ 只改一处出口，逻辑集中。
- **缺点**：要动 `build_kb_v2.py`（公共面代码）→ 须备份 + 评测回归。
- **改动量**：约 3~5 行（import + 两处出口包一层）。
- **已备好**：`本地知识库\text_clean.py`（189 条映射表 + `clean_text()`，已自测通过）。

### 路径 B：先清洗 text_cache，再派生

**做法**：复制 `text_cache_zhenti2` → `text_cache_clean`，逐 txt 清洗，再 `--text-cache text_cache_clean` 派生。

- **优点**：不动代码。
- **缺点**：🔴 **只覆盖 233 个文件**，其余 1800+ 文件仍是脏的 → **清洗不完整**。
- **适用**：只想快验证效果时用。

### 路径 C：派生后直接改 metadata.json 的 text

**做法**：`v10 → copy → v11`，遍历 v11 的 `metadata.json` 清洗 `text` 字段。

- **优点**：最快（不用重跑解析）。
- ⚠️ **但向量是用旧正文算的** → 清洗后**必须重算嵌入**，否则正文与向量不一致。
  → 那还不如走路径 A（反正都要重嵌入）。
- **结论**：**不推荐**。
