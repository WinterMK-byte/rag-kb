## 一 · 行动项①复核：C/E 确实修好了，但 c05 仍 miss 的真因**不是缓存**（已实测排除）

**先确认工兵的成果（我独立复跑，认可）**：C/E chunk0 文本已与 v10 一致（工兵 cos=1.0）。

**但 c05 为什么还是 miss？** 我把整条链路拆开，拿到两个决定性证据：

### 证据 1：appendix 从来没靠 dense 召回，两库都是靠 BM25 → 所以「文本变好」帮不上忙

| 指标 | v10 | v11 |
|---|---|---|
| appendix_C 片段数 | 60 | 60（同） |
| appendix_D 片段数 | 37 | 37（同） |
| appendix_E 片段数 | 60 | 60（同） |
| appendix_C 最佳 dense 排名 | 1725 | 1677（**略变好**） |
| appendix_E 最佳 dense 排名 | 225 | 216（**略变好**） |
| dense top50 里 appendix 占席 | **0** | **0** |

→ **两库里 appendix 都不进 dense top50**。它靠 BM25 进候选，再靠 LLM 重排上位。
**所以「修文本」对本条几乎无收益（文本确实更好了，但本来就不是它挡住的门）。**

### 证据 2：真因 = `cands_n=30` 硬截断，v11 里 appendix 被挤出线外

`retrieve()` 的 `cands_n=30` 是**硬截断**（候选池只有 30 条能进重排，池外无解）。

```
v10：appendix_E = fused F26、appendix_C = fused F29  → 都在 30 条线内 ✅ 进重排 → 最后 rank1 / rank4
v11：appendix_E = fused F28、appendix_C = 掉出 F30   → C 被截断，D 顶上来 ❌
```

**验证（决定性）**：把 `cands_n` 从 30 放大到 80：

| cands_n | v10 | v11 |
|---|---|---|
| 30 | E=**1**, C=**4** ✅ | E=14, C=**未进** ❌ |
| 80 | E=7, C=13 | E=**3**, C=**6** ✅ |

→ **cands_n=80 时 v11 的 appendix_E/C 立刻回到 rank3 / rank6。** 证明**文本内容没问题，纯粹是被截断挡住了。**

### 证据 3：为什么 v11 的 fused 会多占 2 格？——**P0-4 新增的 113 个零正文空壳**

```
v10：META_ONLY_EXT 空壳片段 = 0 个
v11：META_ONLY_EXT 空壳片段 = 113 个   ← P0-4 缓存回写引入
    （.swf 36 / .opj 24 / .nb 7 / .circ 6 / .mmap 5 / .opju 5 / .cap 5 / .jpg 5 / .zip 4 ...）
```

**机制**（`build_kb_v2.py` L485-492）：黑名单文件虽然不解析正文，但**依然会建一条 `has_text=False` 的占位片段，并把「文件名」当正文拿去嵌入**（`embed_texts([label])`）。于是 `CPU.circ` 的**文件名本身进了向量**，`rel_path` 里含「计算机组成原理」→ 对 c05 查询密集命中。

**精确位移量（我逐格数出来的）**：

| | v10 | v11 |
|---|---|---|
| fused 前 30 里空壳数 | **2** | **4** |
| fused 前 30 里 `索引.md` 数 | 10 | 10 |
| appendix_E 落点 | F26 | F28 |

→ **净位移恰好 2 格 = 新增的 2 个空壳**（`CPU.circ` F16、`cs3410.jar` F25）。
而 v10 里 E 在 F26，**离 30 线本来只剩 4 格余量** —— 本来就危险，v11 一加就崩。

## 二 · 决策①：是否重嵌 appendix_D

**要重嵌。但请把预期摆正：重嵌 D 不会让 c05 恢复。**

- 🔴 **C/E 的瓶颈在「候选池截断」，不在「文本质量」** —— 修 D 解决不了截断

→ **动作：重嵌 D（同 C/E 手法：移缓存 → `--force-list`）。但必须同时做决策②，否则 c05 还是不恢复。**

## 三 · 决策②：META_ONLY 文件怎么处理（**关键建议**）

### 🔴 不要硬过滤。用「把 has_text 纳入 meta_penalty」

**实测对比（c05，v11）**：

| 方案 | appendix_E 落点 | 说明 |
|---|---|---|
| 基线 | F28 | appendix_C 出线 |
| A 硬过滤空壳 | F24 | |
| **B 空壳 × 0.4** | **F24** | **与 A 完全等价** |
| C `索引.md` × 0.4 | F18 | |
| **D = B + C** | **F14** ⭐ | 安全垫从 2 格扩到 **16 格** |

**三条硬结论**：
1. **乘 0.4 与硬过滤效果完全一样** → **用乘性惩罚，别硬过滤**。硬过滤的风险：万一某个 `.jpg` 文件名恰好是用户想找的，硬丢弃 = 直接丢召回；乘 0.4 还留着它。
2. **`索引.md` 也必须一起处理** —— 它在 fused 前 30 里占 **10 席**（两库都有！），是比空壳**大 5 倍**的浪费。而 `_META_BASENAMES` 里**根本没有 `索引.md`**（只有 readme/说明/license 那类）→ **建议一并加入**。
3. **改完之后对 v10 也有正收益**（v10 的 E 从 F26 → F14）→ **是净改善，不是给 v11 打补偿补丁**。

**改动点（一行级，风险可控）**：
```python
# kb_search_v4.py 约 L1213 的 meta_penalty 阶段，改为同时看 has_text：
ranked = sorted([(i, round(s * (META_PENALTY if (is_meta_file(meta[i]['file_path'])
                                                 or not meta[i].get('has_text')) else 1.0), 4))
                 for i, s in ranked], key=lambda kv: -kv[1])
# 并把 '索引.md' 加进 _META_BASENAMES
```

⚠️ **必须全量回归**：这条改了 `meta_penalty`，会动**所有 34 条**的排序。改完必须跑 `kb_eval.py --both` 对基线（现行 v11 冷/热 = 76.5%，见下节）。

## 四 · 决策③：c05 恢复判定口径

**建议口径（比工兵提的更严，理由充分）：**

| 判据 | 标准 | 理由 |
|---|---|---|
| 主判据 | **appendix_E 回 top5** | Hit@5 是评测指标线 |
| 附加判据 | **appendix_C 也回 top10** | 🔴 **只看 E 会被骗** —— 决策②的定位实验证明：光过滤空壳能把 E 拉回 F24，但 **C 还在 F30 之外**。若只要求"E 回 rank1"，就会漏掉 C 仍在池外这个事实 |

**不接受「E 回 rank1 才算恢复」**：c05 的 expect 是 `[appendix_C, appendix_E]`，**任一命中即 hit**（评测口径）。要求两条都 rank1 是自定难度，无依据。

**综合判据**：`kb_eval.py` 里 **c05 的 rank ≠ miss**（即 E 或 C 进 top5）**且** 手工确认 C 也进了候选池。
