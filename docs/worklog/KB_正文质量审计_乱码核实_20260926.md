### 2.2 那「异常字符」是什么？—— 私有区字体映射

```
U+F0F2 x200   →  ∫  （积分号）
U+F070 x135   →  p
U+F0A5 x108   →  ~
U+F0A2 x84    →  ′  （导数撇）
U+F0A3 x53    →  <
U+F0E5 x51    →  ∑  （求和号）
U+F0CE x15    →  ∈  （属于）
U+F0B1 x17    →  ±
U+F0B9 x12    →  /
```

**共 1181 个私有区字符，873 个可明确对应到数学符号（74%）。**
成因：PDF 里的 `Symbol` / `MT Extra` 字体用**私有区编码**存数学符号，提取时未做字体映射表转换。

**同一批资料里正常符号大量存在**（`→`1433 / `√`800 / `π`468 / `≤`334 / `α`230 / `≥`229 / `∞`216 / `∈`197 = **4293 个**）
→ 说明**绝大多数页面提取是对的**，私有区只出现在少数用了特殊字体的页面。

- **没有产生成片的乱码段落。**

### 唯一真实的 OCR 缺陷：公式排版失真（非乱码）

样张：`lim | =√2，并计算lim`（`x→1` → `|`）、`3∈(a,+∞）`（`∃` → `3`）、`f'(5)=0`（`ξ` → `5`）

这是 **RapidOCR 对数学排版的能力上限**，表现为**形近字误识**（不是乱码，是「认错成另一个正常字符」）。
影响：公式检索不准，但**中文题干、年份、校名、知识点关键词全部正确** —— 这才是检索主力。

## 五、要不要重构？—— 不要；只需 2 个精准小修

### ✅ 建议做（低成本、高收益）

**修 1 · 入库时清洗控制字符（~15 分钟，零风险）**
在 `extract_text()` 出口统一清洗：删掉 C0/C1 控制字符（`\x00-\x1f` 除 `\n\t`）、`\x01` 这类 `.doc` 残渣。
→ 消掉 140 条「控制字符主导」的垃圾片段，顺带让 `has_text` 判定更准。
→ **收益**：减少重排器被噪声干扰。

**修 2 · 建字体映射表，还原 PUA 数学符号（~1 小时）**
准备一张 `Symbol`/`MT Extra` → Unicode 映射表（业界有现成的），提取 PDF 时按字体名替换。
→ 把 `U+F0F2` 还原成 `∫`、`U+F0E5` 还原成 `∑`。**这不是「修复乱码」，是「让公式可被检索到」。**
→ **收益**：数学/物理课件的公式检索准确率提升。
→ ⚠️ 必须**派生新库**（v11），不能原地改 v10。

### ❌ 不建议做

| 方案 | 为什么不 |
|---|---|
| 全库重跑 OCR | **根本没走过 OCR 的东西重跑什么**；且 98.2% 已经可读 |
| 换 Docling / Marker 重解析全库 | 成本 2 小时+、内存占用高；**收益只落在公式符号上**，不值得全库重来 |
| 因为有「乱码」就推倒重构 | 建立在误判之上，会白扔 2 小时 |
